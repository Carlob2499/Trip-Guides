### (C) Interaction Patterns and Constraints
*   **Three-Tier Offline Architecture:**
    1.  **Web Map Areas:** Defined by admins; cached on the server; scalable for large teams.
    2.  **On-Device Creation:** Defined by users via pan/zoom; generated on-demand; high server load if used by many simultaneously.
    3.  **Mobile Map Packages (MMPKs):** Sideloaded or downloaded; supports complex symbology and routing; **view-only** (no data capture).
*   **Basemap by Reference:** A critical design pattern where a large, static basemap (TPK/VTPK) is sideloaded once. Multiple smaller "operational" offline areas then reference this local file instead of downloading redundant tile data.
*   **Sync Patterns:** Supports manual sync or auto-sync (e.g., 15-minute intervals). If a connection fails during auto-sync, the process enters a "hold" state and resumes immediately upon re-establishing connectivity.
*   **Technical Limits:**
    *   Maximum of 16 pre-defined map areas per web map.
    *   Tile export limits: 150,000 tiles for raster basemaps; 10,000 tiles for vector basemaps.
    *   Spatial reference must be identical between the web map's default basemap and any sideloaded reference basemaps.

### (D) Usability Risks
*   **Destructive Updates:** Changing a map's schema (adding/removing fields) invalidates all existing server-side packages. Users must re-download everything, which can lead to data loss if they have unsynced edits.
*   **Indeterminate Progress:** Large map areas can take significant time to "package" on the server. Without the "Generating" status indicator, users may assume the system has crashed.
*   **Reference Mismatch:** If a "Basemap by Reference" file is missing or renamed on the device, the app may fail to open the offline area or revert to a low-detail default, breaking the user's situational awareness.
*   **Storage Exhaustion:** On-device map creation lacks the guardrails of admin-defined areas, potentially allowing users to attempt downloads that exceed device storage or server timeout limits.

### (E) Non-Authoritative Transferable Observations (for a Traveler PWA)
*   **Progressive Disclosure of Detail:** The "Level of Detail" picker (Room -> Building -> Street -> City) is a highly effective way to manage download size expectations for travelers.
*   **The "Base + Layer" Model:** For a travel app, sideloading a "Country Map" once and then downloading specific "City Itineraries" as small operational layers is a superior architecture to downloading a full map for every city.
*   **Connectivity Resilience:** Implementing a "hold and auto-resume" sync logic is vital for travelers moving through airports, subways, or remote areas with spotty Wi-Fi.
*   **Feature-Granular Downloads:** Allowing users to choose "Text Only" vs. "Text + Photos" for offline guides mirrors the "Features only" vs. "Features + Attachments" toggle used in field workflows.

### (F) Non-Requirement Concepts (Implementation Specifics)
*   **The 16-area limit:** This is a specific constraint of the ArcGIS backend, not a universal UX requirement.
*   **MMPK View-Only status:** This is a limitation of the current ESRI file format; a general design should aim for data capture in all offline modes.
*   **The 150k/10k tile export caps:** These are service-level limits for ESRI's hosted basemaps, not a benchmark for all mapping engines.
*   **Requirement for ArcGIS Pro:** The need for a heavy desktop GIS to create packages is a toolchain dependency, not a workflow requirement for the end-user.
